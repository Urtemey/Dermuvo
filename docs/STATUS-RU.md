# Срез Durevo: что реально готово

Дата: 2026-09-17. Проверено по текущему исходному коду, логам и повторному запуску демонстрации.

## Вердикт

Рабочий инженерный прототип отдельных механизмов защиты и упаковки. Не готовая защита
Юного кодера, не аналог Denuvo по доказанной стойкости, не релиз для школ.
Полная игра не проходила приёмку под защитой. Следующий приоритет — интеграционный пилот
на копии актуального игрового билда, производительность и расширение защиты ценных методов.

## Реализовано

- CLI .NET 10: анализ DLL, точный выбор методов, преобразование с отдельным выходом.
- Базовая обфускация: перестановка блоков с сохранением границ обработчиков исключений,
  сокрытие строк, маскирование целых чисел. Переименования типов/методов нет.
- VM для ограниченного набора статических методов: int/bool/char, циклы, ветвления,
  ограниченные операции со строковыми параметрами. Общие объекты, большинство вызовов,
  обработчики исключений в VM и многие типы ещё не поддерживаются.
- AES-GCM для VM-программ, управляемый и native-интерпретаторы Windows/Linux.
- Загрузка native-модуля из проверенного подписанного снимка.
- Подписанные лицензии, grants, независимые ключи групп, проверка прав и срока действия.
- Подписанная политика групп ключей; выдача grants по этой политике.
- Сборка релиза с проверкой входных хешей, преобразованием DLL, добавлением зависимостей,
  подписью, проверкой и публикацией в новый каталог.
- Дифференциальные тесты, проверки некорректных данных и воспроизводимые атакующие пробы.

Последний начатый переход к grants, привязанным к конкретному релизу, не реализован:
прерванный ход содержал только чтение кода. Формат grants остаётся DUR-KGR1.

## Что проверено в игре и вне её

Последний полный набор: Windows 143810 проверок, Ubuntu 143822. Это повторные проверки
поведения и ошибок, не число защищённых функций и не показатель сложности взлома.

Изолированные Unity 6000.3.22f1 Windows/Linux x64 Development Players прошли соответствующие
smoke-проверки runtime, подписей, загрузки и отдельных преобразованных методов.
Linux проверялся в Ubuntu, в том числе headless. Игра настроена на Unity 6000.3.23f1.

Пилот трёх игровых DLL использовал сохранённые, а не заново собранные текущие файлы:
- JuniorCoder.LicenseKey.dll: 4 метода базовой обфускации;
- CodeAnalyzer.dll: 10 методов базовой обфускации;
- JuniorCoder.GameScene.dll: один строковый парсер Python в encrypted verified-native VM.

Пакетный пилот прошёл 25 целевых проверок на каждой платформе.
Он не является установкой полной игры.

Аудит 21 сохранённой сборки: 14922 тела методов, включая сторонний/генерируемый код.
14501 статически допускают базовый проход; это не разрешение массово включить его.
VM допускает лишь 10: 6 сторонних, 3 простых собственных и один игровой парсер.
Вся Scratch/Python/ML/кооперативная логика не виртуализирована.

Не проверены: полный игровой сеанс, запуск всех уровней, полный цикл Scratch/SB3,
обучение ML, несколько клиентов в LAN, обновление/восстановление защищённой игры,
актуальный Unity 6000.3.23f1, DEB/RPM на Debian/Astra/РЕД ОС/ALT.

FPS, время загрузки, RAM и размер полного защищённого релиза не измерены.
Утверждать, что защита не замедляет игру, нельзя.
git status --short --untracked-files=no для JuniorCoder сейчас пуст:
отслеживаемые рабочие файлы игры не изменены. Это не тест её работоспособности.

## Реальная стойкость

Базовая обфускация затрудняет чтение, но не делает код недоступным.
Незашифрованную VM уже удалось восстановить статически.
Шифрование скрывает VM-программу от анализа одного файла без ключа.
Однако извлечение ключа из лицензированного процесса воспроизведено и для native-модуля.
С извлечённым ключом методы запускались после истечения лицензии.

Подпись обнаруживает изменение файлов только при выполнении доверенной проверки.
Защита проверки от изменения атакующим не доказана.
Нет независимой оценки времени взлома или измеренного замедления реверса с ИИ.
Нет безопасной доставки ключей конечному клиенту.
Grants не привязаны к хешу релиза; повторное использование ключей требует осторожности.
Независимые ключи ограничивают последствия утечки одного ключа, но доступный процессу
набор ключей также можно пытаться извлечь целиком.

## Как предполагается включать в выпуск

1. Собрать обычную игру в отдельный каталог.
2. Через analyze определить совместимые методы; сформировать явный план с входными SHA-256.
3. Для VM подготовить внешние ключи и политику групп, для подписи — ключ издателя.
4. protect-release / protect-release-keyring создаёт новый преобразованный подписанный каталог.
5. В bootstrap игры интегрировать проверку доверенной подписи, получение ключей,
   активацию разрешений до первого вызова защищённого метода и управление временем их жизни.
6. Пересоздать игровые манифесты обновлений/пакеты и пройти продуктовые сценарии.

Пункты 5-6 для полной игры ещё не выполнены. Подмена DLL вручную — не готовая интеграция.
VM-методы без активированного ключа намеренно перестают исполняться.

## Качество и состояние разработки

Сильная сторона: явные границы поддержки, отказ при несовместимости, сравнение результатов
с оригиналом, тесты с положительными контролями атак. Криптографические примитивы взяты
из платформенных/готовых библиотек.

Слабая сторона: малая полезная VM-совместимость, незакрытое извлечение ключей,
нет полного продуктового прогона и профилирования. Исторические документы содержат
результаты разных этапов; этот срез и последние логи имеют приоритет над ранними цифрами.

В Durevo исходные файлы всё ещё показываются git как untracked; полноценная история
зафиксированных изменений отсутствует. Перед следующими крупными работами нужен
зафиксированный исходный базис. В этом срезе коммит и публикация не выполнялись.
